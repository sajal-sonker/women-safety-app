## 2. Common wire rules

- `/v1`, JSON UTF-8, HTTPS except loopback/local development. UUIDv4 canonical strings; UTC RFC3339 with `Z`, finite numbers, no client-supplied owner IDs. Timestamps returned by server include `server_time`; domain snapshots include `schema_version:1`, `revision` (monotonic integer per aggregate), and `updated_at`.
- Coordinate fields are `{lat,lon}` in degrees WGS84; GeoJSON is `[lon,lat]`; PostGIS construction is `(lon,lat)`. Distances/accuracy metres; duration seconds; battery integer 0–100. No implicit milliseconds. Location source enum `gps|network|last_known|manual`.
- `Location = {lat,lon,accuracy_m:number|null,captured_at,source}`; latitude [-90,90], longitude [-180,180], accuracy finite 0–100000 when supplied. Reject malformed points independently of SOS creation: mobile sends null location and warning when no valid point. Future >60s timestamp is invalid; stale initial location is accepted and labelled. Ongoing points older than the stored latest never replace it; duplicates return existing receipt. Points older than 24h return `422 STALE_LOCATION`; initial SOS can still include a labelled old fix. Server receive time is independent.
- Location `CURRENT` requires captured age <=60s and accuracy <=100m; `APPROXIMATE` for fresh coarse/unknown accuracy; `STALE` if older; `UNAVAILABLE` if null. Contact ranking requires age <=300s, accuracy <=100m, valid consent, active TTL and verified identity. Freshness is recomputed at read, never cached as permanently current.
- Lists: `{items:[],next_cursor:string|null}`; opaque cursor, default 20/max100; stable `(created_at,id)` order. No offset exposed. All fields in catalogue types are required unless suffixed `?`; unavailable fields are nullable where specified. Reject unknown request properties, disallow nonfinite numbers, bound strings/arrays. Error `{error:{code,message,request_id,retry_after_s?:number}}`; always echo/generate validated UUID `X-Request-ID`. No stack, phone, token, coordinates or raw payload in errors/logs.
- `400 VALIDATION_ERROR`; `401 UNAUTHENTICATED`; cross-owner lookup `404 NOT_FOUND`; `403 FORBIDDEN` for known role failure; `409 IDEMPOTENCY_MISMATCH|INVALID_TRANSITION|INTENT_TERMINATED|ACTIVE_JOURNEY_EXISTS`; `410 GRANT_EXPIRED|GRANT_REVOKED`; `422 STALE_LOCATION|PERMISSION_UNAVAILABLE`; `429 RATE_LIMITED`; `503 DEPENDENCY_UNAVAILABLE|FEATURE_DISABLED`. `Retry-After` accompanies retryable responses.
- All POST/PATCH/PUT/DELETE mutations require `Idempotency-Key` UUID except token exchange/logout, provider callbacks and idempotent position writes (which use `sample_id` UUID). Header equals `client_request_id` on SOS. Idempotency key is scoped to principal + operation + resource; canonical body hash mismatch is 409. Return 201 first create, 200 replay with `Idempotency-Replayed:true`, 204 deletes, 202 asynchronous jobs. Keep general keys 24h; SOS dedupe/tombstones persist 30d with event summary. Do not treat external delivery as exactly once.

## 3. Authentication, consent and roles

Mobile and authenticated browser actions use Firebase **ID** tokens, not custom/refresh tokens, verified by Admin SDK signature/issuer/audience/expiry and allowed project. Backend maps UID to internal UUID; disabled/deleted app-user checks occur every request. Default `verifyIdToken` does not check revocation; explicitly check revocation for privileged/session-establishment and consent/security mutations. Ordinary SOS verifies JWT with cached signing keys and local disable status; document token's maximum one-hour residual revocation exposure, invalidate via local disable on account deletion, never fail open if verification cannot be established. Refresh once on 401 using SDK; preserve SOS UUID, do not loop OTP in emergency. Dialer remains available without auth.

Auth emulator enabled only with explicit local environment and host check; process refuses emulator configuration in staging/pilot. A provider outage never permits arbitrary unsigned tokens. Admin roles come from server `role_assignments`, cannot be set in profile updates or trusted from client claims. Roles USER, SHOP_OWNER, MODERATOR; CONTACT is an event/relationship scope, not a global read role. SUPPORT has no private-data capability in v1; no break-glass endpoint is implemented.

Contact invite is 256-bit random, hash stored, 24h expiry, single **accept/decline** decision. GET landing page is inert. After web phone OTP, `POST /contacts/invitations/accept` checks invite token, matching verified Firebase `phone_number`, invited owner/contact not revoked, and consent version. Forwarded token with wrong phone fails. Decline/withdrawal suppresses further invitations until contact deliberately opts in again. Browser may then create 15-minute HttpOnly identity session via verified-token exchange; SameSite=Lax, Secure, host-only and CSRF/Origin protection on all cookie mutations. Contact may optionally use bearer auth. Contact GPS requires another explicit start action (default30min, max2h); only latest position retained; no owner endpoint returns that GPS.

Owner can store 0–5 contacts; onboarding recommends 3–5. Verified contacts receive initial SOS; pending/revoked/declined never receive it. Zero eligible contacts **must not reject SOS**. Editing phone creates a new invitation relationship instead of silently reusing verification. Soft removal revokes consent/grants/location sessions and suppresses unsent notifications; retain minimal recipient snapshot for audit.

Browser contactGPS operates only while browser grants/maintains foreground geolocation; page-hidden/locked behavior is not guaranteed. Display pause/staleness and let5min freshness exclude it from ranking. Do not infer continued movement from an open session.

## 4. SOS transaction, states and races

### Distinct state axes

| Axis | Values / interpretation |
|---|---|
| Event | `CREATED, DISPATCHING, ACTIVE, RESOLVED, CANCELLED`; terminal states never reopen. CREATED→DISPATCHING when a worker starts an attempt, DISPATCHING→ACTIVE after outcome recorded. Zero-recipient events remain CREATED until resolved/expired. CREATED/DISPATCHING/ACTIVE may resolve. |
| Dispatch summary | `QUEUED, IN_PROGRESS, ATTEMPTED, NO_ELIGIBLE_RECIPIENTS, STOPPED`; it never says delivered. |
| Channel | `PENDING, QUEUED, PROVIDER_ACCEPTED, DELIVERED, FAILED, UNKNOWN, SUPPRESSED`; acceptance/unknown is not handset delivery. DELIVERED requires provider capability + authenticated receipt. |
| Acknowledgement | `PENDING, CAN_ASSIST, CANNOT_ASSIST`; independent of channel state. Latest explicit response + ETA is versioned/audited; can-assist may later change to cannot-assist. |
| Job | `PENDING, LEASED, RETRY, COMPLETED, DEAD, SUPPRESSED`; retrying is not losing intent. |

SOS POST transaction: lock user's intent key; compare immutable body hash; insert event, verified recipient snapshots, grants and initial per-channel intents plus escalation job. Read contact GPS already in DB with a bounded query only; use configured priority when unavailable. Commit before response. No network provider, fresh-fix wait, media, geocoder, map, ML or route call inside transaction. Initial response has `status:CREATED`, `dispatch_status:QUEUED` or `NO_ELIGIBLE_RECIPIENTS`, null location when absent, `eligible_recipient_count`, `expires_at`, and `replayed` boolean. Invalid optional context is omitted with warning by client; server still enforces JSON schema. UI does not manufacture server acceptance when HTTP result unknown.

Distance ranking also requires the owner's position age≤60s/accuracy≤100m; stale/coarse/unavailable owner origin forces configured priority even if contacts have freshGPS. No fresh-fix wait. A later promotion may use newly accepted current owner position and current contact consent, never override a recorded CAN_ASSIST silently.

One event per `(user_id,client_request_id)`, not per account forever: genuinely different manual activations may create separate events. UI coalesces a physical double-tap/same active action; new-event confirmation is deliberate. Server-generated journey SOS uses a unique `(journey_id,escalation_version)` key and same transaction routine, `JOURNEY_OVERDUE` unavailable to ordinary mobile POST. Experimental triggers require capability enabled; manual always accepted.

Cancellation: local countdown may end before any POST. `/sos/:id/cancel` succeeds only if CREATED, no leased/attempted job and suppression atomically wins event lock; else409 INVALID_TRANSITION with error.recovery_action=RESOLVE_EVENT. No ACTIVE→CANCELLED operator transition. `/resolve` immediately marks terminal, revokes sessions/grants, suppresses pending jobs and ends GPS. An already in-flight provider request may arrive; neither endpoint can retract it. Explicit FALSE_ALARM resolution may enqueue one minimal correction per previously attempted recipient, without live location/grant. Late receipts can update audit but never resurrect event/access.

Each event has a hard24h lifetime; no event-extension endpoint exists in v1. A longer need requires a new deliberate authenticated SOS after explaining renewed sharing. Grant reissue does not extend event expiry. Expiry resolves with `EXPIRED`, revokes access and ends sharing; history distinguishes user resolution from expiry. Contact can withdraw without resolving owner's event. Resolution reason `SAFE|FALSE_ALARM|EXPIRED` (EXPIRED server only).

## 5. Offline journal and terminal intent

M persists, encrypted/account-bound: intent UUID, original trigger time, immutable POST payload/hash, account UID, transport state, event ID if known, retry deadline, terminal tombstone and pending resolution. Kotlin and JS use one journal/UUID. State: `LOCAL_PENDING → IN_FLIGHT → SERVER_ACCEPTED`; uncertainty `OUTCOME_UNKNOWN`; terminal desire `STOP_REQUESTED`; unsent age>5min `RECONFIRM_REQUIRED`. Backoff 1/2/4/8/16/30 seconds with jitter while session active; do not create new UUID/body on retry. Refresh location only through append after event accepted. Never automatically replay an intent from another login, a locally ended session, or beyond 5min. Reconfirmation creates a new deliberate activation; old intent is terminalized first.

GET `/sos/by-client-request/:clientRequestId` reconciles ownership and current result; 404 alone is insufficient to beat an in-flight create. POST `/sos/intents/:clientRequestId/terminate` under the **same intent lock** inserts terminal tombstone if absent, or resolves existing event; a late create then returns409 `INTENT_TERMINATED`. Mobile sends termination when online after local cancel/stop and repeats until acknowledged. If offline, UI says sharing/delivery stop unconfirmed; it cannot assert server revocation. Local timers do not imply server escalation cancellation. Journal survives process death; logout suppresses replay and requests terminalization/revocation before discarding credentials when possible. Secure journal expiry30d prevents indefinite personal records; unresolved ambiguity is visible on next same-account login.

Retain the sensitive immutable journal payload only while a permitted create retry is pending≤5min. On acceptance/stop/reconfirmation expiry, remove coordinates/context/body and retain UUID/hash/account/transport+terminal state for reconciliation, bounded30d. A hash/intent key permits reconciliation without resending expired body.

## 6. Delivery, escalation and notification payloads

Initial SMS intent for every verified contact; push only when that same contact principal has a registered device and a permitted provider adapter. SMS-only is valid, no invented FCM token for a phone number. Initial dedupe `(event,recipient,channel,INITIAL,1)`. Primary context uses already available fields; enrichment updates portal without mandatory repeated SMS. Promotion after30s with no CAN_ASSIST, or immediate primary CANNOT_ASSIST, locks event/recipient ranks and creates one deduped promotion intent. Choose next untried eligible contact; stop reminders when one accepts, all exhausted or event terminal; one promotion per contact per event, no infinite cycling. Initial messages to all are never withheld by ranking.

Worker leases ready jobs `FOR UPDATE SKIP LOCKED`, bounded batch20, lease30s, provider timeout10s outside DB transaction, lease renewal on long work, attempt records before/after call. Retry transient definitive failures at 5/15/45/120/300s with jitter, maximum5 attempts within10min or grant expiry; respect Retry-After; permanent reject goes DEAD immediately. Unknown outcome enters reconciliation, use provider idempotency key if supported; absent reconciliation/idempotency, at most one explicitly labelled ambiguous retry under adapter policy and record duplicate risk. No promise of exactly-once network send. Resolve/revoke checks both before lease and before call; unavoidable in-flight race is reported.

Callback verifies provider signature over original bytes, timestamp/replay bounds and configured account; persist unique provider callback ID, map only known message reference; no caller-supplied event authorization. Reducer never downgrades DELIVERED to accepted/failed because receipts arrive late. FCM acceptance cannot establish DELIVERED. Fake-provider simulated receipts are labelled simulated. Live provider enablement requires [R01/D30](TECHNICAL_RISKS_AND_DECISIONS.md).

Provider-neutral internal `alert_v1`: `{schema_version:1,notification_id,event_id,kind:INITIAL|PROMOTION|CORRECTION|JOURNEY_CHECKIN,locale,enqueued_at,expires_at,recipient_ref,template_version,grant_ref?,context_ref?}`. Adapter resolves encrypted recipient/material only server-side. Push wire data `{schema_version:'1',type:'SOS_AVAILABLE',event_id,notification_id,created_at}`; no coordinates, battery, evidence, PIN, phone or tracking bearer. User-visible generic notification + authenticated fetch; device token never acts as authorization. SMS uses generic emergency text and secure link, no raw coordinates/media. Detailed `alert_v1` context in old flow is a **portal view**, not the lock-screen/public SMS payload.

Domain revision events (durable in `domain_events`) `{schema_version:1,event_id,revision,type,occurred_at,payload}`; types `SOS_CREATED,DISPATCH_UPDATED,POSITION_UPDATED,CONTEXT_UPDATED,RECIPIENT_ACKNOWLEDGED,PRIMARY_PROMOTED,SOS_RESOLVED,ACCESS_REVOKED`. Payload is changed field names/status/references, not tokens/media. B derives owner/recipient filtered snapshots; no public event bus. Poll `/tracking/event?after_revision=N` and owner detail; response200 snapshot or204 unchanged with server-time header. Location cursor is opaque `(received_at,id)`, max100, not trusted client timestamp. Revision assigned transactionally, never decreasing; a later-arriving old GPS sample cannot overwrite current position.

## 7. Tracking grants and sessions

Link `/track#token=<256-bit-base64url>` preferred; legacy path link must redact ingress logs. First-party bootstrap strips fragment via `history.replaceState` before loading maps; inert GET cannot consume grant, to tolerate link scanners. Recipient explicitly opens alert, then POST exchange. Grant2h, same recipient/event/scopes; short cookie session15min idle, absolute2h bounded by grant/event expiry. Single exchange per grant with same-session retry; deliberate owner renewal/reissue revokes previous grant and creates new2h grant only while event active. Lost/forwarded bearer is a documented risk; exact phone identity is enforced for contact-consent/GPS, not falsely implied by bearer tracking. No third-party analytics/scripts on tracking landing; hosted map tiles can reveal viewed area, so use approved privacy-reviewed host and disclose it. Public OSM tile service conflicts with required no-referrer policy; do not use it on this page.

Store token hash in grants; encrypted short-lived token/message material in outbox is an explicit necessity for delivery retries. Purge ciphertext on completed/dead/expired grant. Browser session stores only random hash and grant FK; every read, ack and media request checks event active, grant expiry/revocation, recipient consent and session expiry. CSRF token + Origin check required for cookie mutations. No caching, service-worker cache, referrer or indexing of private content.

Recipient allowlist: event ID/status/start time, trigger class, shared display name, current position/accuracy/age, allowed context with freshness, own acknowledgement/role, anonymous count of assisting responders, authorized evidence metadata. Never owner history/profile, contact phone list, other recipient identity/GPS, journal, PIN, raw audit or private routes. Evidence access requires separate owner consent selecting recipient scope. Moderator has no event access. Resolve/logout/revoke clears map state and cached coordinates.

## 8. Journey, sharing and race policy

One ACTIVE/OVERDUE journey per user; start requires auto-escalation toggle and selected verified contacts (may be zero with explicit warning). Default `auto_escalate:true`, `share_with_contacts:false`, grace120s, duration max12h. Persist `deadline_version`, `checkin_due_at`=ETA, `escalate_at`=ETA+grace, sharing consent, and unique source-SOS FK. At ETA lock row, set OVERDUE, enqueue user check-in, no SOS yet. At grace lock/re-read version/status, atomically create SOS and set ESCALATED. Arrival/extension racing worker uses same lock: whichever commits first governs; arrival after escalation does not silently resolve SOS, returns `sos_event_id` and requires explicit resolution. Cancellation after escalation ends journey only, alert must be resolved separately.

SAFE check-in means ARRIVED (explicit UI wording); EXTEND adds 1–60min from `max(server_now,expected_arrival_at)` and increments deadline version; NEED_HELP immediately creates linked SOS, no grace. If auto_escalate=false, overdue remains visible but never creates SOS; show that choice. Pings/check-ins cannot extend without authenticated action. SMS/push check-in delivery failure cannot stop server overdue processing.

Journey points use sample IDs, same location validation, retention and foreground location lifecycle; recipient journey grant only if user selected sharing, type `JOURNEY_READ`, no evidence/history. Journey resolve/arrival/expiry revokes it. Journey can run without sharing (server timer still works). On escalation revoke journey grants, create separate SOS grants and fanout; no scope widening of an old token. Mobile server state remains authoritative after process death.

## 9. Routing, shops, reports and media

MapsProvider boundary: `candidates({origin,destination,depart_at,mode:'walking',max_candidates:3}) → {provider_version,data_version,routes:[{provider_id,geometry:GeoJSON.LineString,distance_m,eta_seconds,segments:[{segment_ref,geometry,distance_m,duration_s}]}],warnings}`. Router client timeout5s, circuit breaker; no SOS dependency. GraphHopper unit/order/edge-mapping conformance is mandatory. Geocoder `reverse(point) → {label,source,observed_at}|null` timeout2s best effort; tiles configured separately. Fake, self-hosted GraphHopper and approved hosted adapters share contract; no public Nominatim/autocomplete dependency.

Route scoring uses [07](07_TIME_AWARE_ROUTING.md), effective coverage incorporates quality/freshness not just non-null fields; below0.50 score null. `confidence` means feature coverage estimate, never probability. Return fewer than3 candidates with `alternatives_reason` when topology insufficient; same geometry may fill multiple role labels without creating duplicate route IDs. No global optimum claim. All providers/scoring outages return safe/legal route if available, null indicator and reasons; if router fails return503, retain manual SOS and journey destination/ETA entry.

Shops: only active, owner-consented records public as participants; OSM POIs separately labelled candidates. `CONFIRMED_OPEN` only if owner confirmation<=30min and not schedule-closed/paused/revoked; otherwise scheduled/unknown/closed. Owner confirmation never overrides explicit closure. SHOP-03 requires owner agreement version + user event selection; shop-specific grant current position/arrival context only, TTL15min, no evidence/contact details. Shop recipients stored separately; cannot enter trusted-contact ranking. No agreement means FEATURE_DISABLED.

Report categories `LIGHTING, HARASSMENT, ROAD_OBSTRUCTION, OTHER_CONDITION`; strip PII, text<=1000. Pending input never public/scoring; moderator removal returns APPROVED→WITHDRAWN with reason. Public output aggregates snapped ~250m cells, suppresses counts<3 independent reporters; never exact incident/victim coordinates. Deduplicate user/category/cell/24h; decay half-life30d, expire90d. These are pilot modeling/privacy defaults, not validated risk statistics.

Evidence presign input records kind `AUDIO|PHOTO|VIDEO`, MIME allowlist, exact size/hash, captured_at, consent version and explicitly selected recipient IDs. Max AUDIO10s/2MiB, PHOTO5MiB, VIDEO10s/10MiB. Signed single-object upload5min to private quarantine; server checks object ownership/hash/MIME/magic/size/duration/EXIF stripping/scan before AVAILABLE. Never trust complete request as scan result. Download streams through API with fresh authorization and no-store, no public/presigned read URLs. Owner may delete at any time; revoke grants on event end; no replay/capture after consent withdrawal. Storage failure leaves SOS active. Upload/process states `REQUESTED,UPLOADING,QUARANTINED,AVAILABLE,FAILED,DELETED`; metadata contains no public object key.

### Tracking exchange recovery and cookie isolation

POST /tracking/exchange input is {token,exchange_id:UUID}; output {grant_id:UUID,grant_kind:SOS_READ|JOURNEY_READ|SHOP_ALERT,expires_at,csrf_token}, sets host-only HttpOnly Secure SameSite=Lax cookie and returns no raw session secret. Browser persists random exchange_id in sessionStorage for this pending grant beforePOST; retries use identical pair. First exchange binds the grant to a hash of exchange_id. Same pair may retry for120s without extending expiry and receive the same encrypted pending cookie material; other exchange IDs fail409 CONFLICT. After120s, existing cookie resumes or owner must reissue. Purge encrypted recovery material at120s. Apply strict exchange rate limit; GET/link scanner cannot consume token.

Cookies are named per opaque grant UUID, not one global tracking cookie. Scoped endpoints accept X-Tracking-Grant-ID matching the named cookie, then enforce event/recipient/scopes; UUID is a selector, never authority. This prevents two tabs/events silently replacing each other's scope. Store grant selector/CSRF only in sessionStorage, strip token fragment before external resources. Multiple tabs with separate exchange IDs require existing valid grant cookie or a new reissued grant; show deliberate recovery rather than consuming silently. Cookie expiry is min(grant expiry,event expiry,2h absolute) with15min idle. Identity/admin cookies use a separate namespace. Logout invalidates the selected tracking session only; account logout revokes its identity sessions/devices.
