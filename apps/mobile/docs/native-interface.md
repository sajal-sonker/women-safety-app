# Native Phase 1/2 boundary

Source of truth: [NativeSafety.ts](../specs/NativeSafety.ts), Codegen TurboModule. [SafetyRuntime.kt](../android/app/src/main/java/com/surakshaai/SafetyRuntime.kt) owns Firebase auth, HTTP, encrypted journal and retries. JS does not store raw bearer tokens or implement a competing SOS retry queue. Generated Kotlin DTOs and contract hash come from the root OpenAPI generator.

`initialize` accepts the generated contract hash and an optional allowed local-debug base URL. `startPhone`/`confirmPhone` use the native Firebase SDK. `apiRequest` refreshes auth once and generates ordinary mutation keys; `activateSos` persists one immutable account-bound UUID/payload before network. `getSafetyState`/`onSafetyChange` return a redacted journal projection. `terminateIntent` stops local tracking and persists termination before attempting server reconciliation. `startLocation`/`stopLocation` reference-count purpose+resource; stopping one purpose cannot stop another active purpose. `clearAccount` refuses while server/local SOS or journey work is active.

States: LOCAL_PENDING → IN_FLIGHT → SERVER_ACCEPTED; uncertain network outcomes become OUTCOME_UNKNOWN and reconcile by the same intent. Unconfirmed attempts older than five minutes become RECONFIRM_REQUIRED; there is no unbounded silent create retry. STOP_REQUESTED remains visible until the server confirms termination; then TERMINATED. Stored Android monotonic time and wall time detect age/reboot anomalies. Journal is AES-GCM encrypted under Android Keystore; app backups are disabled. Native auth identity must match the persisted intent before recovery.

Location FGS starts from deliberate visible UI actions, accepts only SOS/JOURNEY/PENDING purpose, expires by monotonic deadline and stops on local termination. PENDING can collect a fix but cannot post to an unknown event. Last-known/null location is included immediately; fresh fixes arrive asynchronously. Accepted SOS reconciles server state every30s while process is alive; service stop does not imply an offline remote resolution. Service is START_NOT_STICKY with no boot receiver. Permission loss/GPS unavailable/service start rejection are degraded states, never delivery success.

`setMonitoring` and advanced trigger seams remain disabled for Phase3. No microphone/camera/SMS/accessibility permission is declared. No global volume-key interception is implemented. Device lifecycle evidence is still required; see [platform-spikes.md](platform-spikes.md).
